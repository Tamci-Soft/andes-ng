# General Guidelines for working with Nx

- For navigating/exploring the workspace, invoke the `nx-workspace` skill first if it is available - it has patterns for querying projects, targets, and dependencies. If it is not, use the Nx MCP server tools instead.
- When running tasks (for example build, lint, test, e2e, etc.), always prefer running the task through `nx` (i.e. `nx run`, `nx run-many`, `nx affected`) instead of using the underlying tooling directly
- Prefix nx commands with the workspace's package manager (e.g., `pnpm nx build`, `npm exec nx test`) - avoids using globally installed CLI
- You have access to the Nx MCP server and its tools, use them to help the user
- For Nx plugin best practices, check `node_modules/@nx/<plugin>/PLUGIN.md`. Not all plugins have this file - proceed without it if unavailable.
- NEVER guess CLI flags - always check nx_docs or `--help` first when unsure

## Scaffolding & Generators

- For scaffolding tasks (creating apps, libs, project structure, setup), invoke the `nx-generate` skill FIRST if it is available, before exploring or calling MCP tools. If it is not available, discover generators through the Nx MCP server.

## When to use nx_docs

- USE for: advanced config options, unfamiliar flags, migration guides, plugin configuration, edge cases
- DON'T USE for: basic generator syntax (`nx g @nx/react:app`), standard commands, things you already know
- The `nx-generate` skill, when available, handles generator discovery internally - don't call nx_docs just to look up generator syntax

## Repository scope

This repository currently contains **only the workspace setup**. There is no component, no design token and no test helper yet, and that is deliberate:

- `packages/ui` and `packages/testing` export nothing; their entry points are `export {};`.
- `packages/tokens/src/theme.css` is a documented, empty entry point. Token names are public API under semantic versioning, so the catalogue is defined together with the first component foundations, not before.
- `apps/playground` is a minimal Angular application, not a demo.

Do not add components, tokens, helpers or demo content unless the task explicitly asks for them. `packages/ui/src/index.spec.ts` and `packages/testing/src/index.spec.ts` assert that these entry points stay empty; if a change makes them fail, that is the signal to confirm the intent rather than to update the assertion.

Spartan Brain and its required peers are installed and declared in `packages/ui/package.json` but intentionally unused, to reserve the contract in [ADR 0004](docs/adr/0004-spartan-brain-behind-andes-adapters.md). They are listed under `ignoredDependencies` in `packages/ui/eslint.config.mjs`; remove each exception when its dependency comes into real use.

## Agent tooling

Only two assistant configurations are kept: `.claude/` and `.codex/`. The Nx AI setup generates the same skills for six assistants at once (`.agents/`, `.cursor/`, `.gemini/`, `.opencode/`, `.github/skills/`, plus Copilot agents and prompts); those were removed on purpose. **Do not re-run the Nx AI setup generator without asking** — it restores all of them.

As a result the Nx skills (`nx-workspace`, `nx-generate`, `nx-import`, `nx-plugins`, `nx-run-tasks`) are not vendored in this repository:

- **Claude Code** receives them from the `nx@nx-claude-plugins` plugin declared in `.claude/settings.json`.
- **Codex** has no skills; use the `nx-mcp` server configured in `.codex/config.toml` instead.

Either way, treat the skills as optional. Fall back to the Nx MCP server tools when a skill is not present.

## Verification

Before proposing a change as finished, run:

```bash
pnpm nx format:write && pnpm lint && pnpm test && pnpm build && pnpm build:storybook
```

If `pnpm` is not on the PATH, use `corepack pnpm` — the workspace pins `pnpm@11.1.1` through `packageManager`.

There is no e2e target: Playwright was removed as out of scope. Storybook builds with no stories, which is expected while no component exists.
